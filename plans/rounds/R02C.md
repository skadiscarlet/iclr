## 4. C02 — 三类输出契约、一个真实可更新的状态

### 4.1 本包已有代码，先运行，不要从零重写

提供：

```text
tests/r02c_contract/test_output_contract.py
schemas/r02c_history_note.schema.json
schemas/r02c_sbs_note.schema.json
schemas/r02c_final.schema.json
```

先实际运行：

```bash
python -m unittest discover -s tests/r02c_contract -v
```

这是纯标准库、无真实数据与模型的测试。集成使用 `from sbs.output_contract import parse_response`。可增加生产适配层，但不能放宽“不改语义/不补答案”的规则。

注意：此模块只判语法、形状和可选 ID membership，**不判真假、不判关系充分性**。已有 binding 仍要校验实例、generation、读取状态、body 和范围。

### 4.2 中间步骤与最终判断分开

旧 runner 每一步都索要最终 verdict，实际上增加了无必要的输出负担。R02C 采用以下确定契约。

**History 的 form/read 步：**

```json
{"note":"A concise account of what is known, what changed, and what remains uncertain."}
```

一段普通笔记，鼓励记录事实、支持/反对当前解释的材料与未知项，但不强制关系字段。生成的笔记按时间追加保存；给下一步时按预先冻结的“最新完整笔记优先”规则，在 512-token note 预算内保留，不能从中人工补推理。

**SBS 的 form/read 步：**

```json
{
  "entities":["program object","calling context"],
  "requirement":"An explicitly sourced requirement, or a clearly marked tentative requirement.",
  "hypothesis":"A specific candidate failure of that requirement.",
  "support_refs":[],
  "counter_refs":[],
  "unknowns":["The applicable requirement has not yet been established."],
  "limitations":[]
}
```

这些是**形状示意，不是所有实例的初始答案**。真实代码中的卡片值必须来自本次模型输出；在第一次成功输出前状态为 not_initialized。不得把示意文字、正确 B、旧 fixture 脚本或 `unit/constraint` 占位强行当有效假设。

SBS 卡片每次整体校验成功后原子替换：entities、requirement、hypothesis、support_refs、counter_refs、unknowns、limitations 都进入后续 prompt。`unknowns=[]` 必须清空旧未知项，不保留过期结论。所有历史原始卡片仍保存。当前卡片序列化后超过 note 预算时记 memory_overflow，不裁掉半个 JSON 后当合法卡片。

**双方 final 步使用完全相同的六键契约：**

```text
hypothesis: 非空字符串，明确某个要求可能失效的命题
verdict: 只能是 "supported" / "refuted" / "unresolved"
support_refs: 已观察 evidence ID 的字符串列表
counter_refs: 已观察 evidence ID 的字符串列表
unknowns: 字符串列表
limitations: 字符串列表
```

不要求模型生成 instance_id、generation_id 或真实源码行号；这些由受信任观察记录按 evidence ID 精确绑定，避免小模型抄内部标识。不能使用“第一条 evidence 的 span”作为其他证据的默认范围。

### 4.3 verdict 极性必须一致

在**每个 final 请求**中提供同一段说明，而不是只放在 E0：

```text
Evaluate the failure proposition stated in hypothesis, not the overall safety
of the project. "supported" means the supplied evidence supports this specific
requirement-failure proposition. "refuted" means supplied counter-evidence
contradicts this specific proposition. "unresolved" means the available evidence
does not settle it. Never use true/false, safe/unsafe, yes/no, or numeric labels.
Return one complete JSON object only; all six keys are required. All reference,
unknowns and limitations fields are arrays of strings. Do not invent IDs.
```

模型可以提出错误或无关的命题，运行器不能偷偷把它改成目标漏洞；语义评分之后单独检查 target alignment。结构正确≠目标正确。

### 4.4 失败处理：重新生成不是“仅格式修复”

- 首次输出始终保留和计入 first_attempt 指标。
- 包装归一化由确定性代码完成，不耗模型请求。
- 仍不合格时每个逻辑请求最多允许**一次新生成**：给原输入、完整输出契约、上次原响应及错误代码；不提供金标准、补丁、正确引用建议、目标真假。
- 这是 `schema_reprompt`，**不是保证语义不变的格式修复**。新输出可能改变命题或结论，必须独立保存并记录可比较字段是否变化；不得把它替换进旧 raw。
- 若同样失败，停止该 episode：`execution_status=output_contract_failed`，`model_decision=null`，保留此前有效状态。执行器可标 `terminal=UNRESOLVED`、原因 output_contract_failed，但不能伪造成模型回答了 verdict=unresolved。
- 每个逻辑请求仅采纳按规则出现的第一个完整合格输出，不 best-of-N，不按漏洞答案挑选。
- E0 与 E1 使用相同归一化/重试规则；不为 SBS 单独多给机会。

### 4.5 修正真实状态更新和终止

1. 每一步都区分 raw、schema_valid、reference_valid、state_applied；日志明确记录 pre/post state hash。
2. History 保存普通笔记；SBS 保存模型生成的完整当前卡片。不得继续只保留 hypothesis 文本而丢弃全部证据关系。
3. 卡片替换后内部 hypothesis revision 递增并绑定新文本；旧命题的支持/反证不得自动继承到新命题。模型明确给出且通过当前观察检查的引用才能留下。
4. 引用校验失败时整次状态更新不应用，不静默跳过坏引用后留下好引用。
5. 最终 supported 必须有可绑定的 support_refs，refuted 必须有可绑定的 counter_refs；这是**最低证据形式要求**，不是证明结论正确。
6. 有效 final 显式终止：supported/refuted → FINISH；unresolved → UNRESOLVED。无 valid final → executor UNRESOLVED + model_decision=null。
7. 将“没有预算继续读”与“现有证据不足”分开。预算刚好耗尽不应自动抹掉已经完整形成的有据结论；但缺材料/失败时不能由执行器创建肯定或否定结论。只对新 frozen-pilot 路径修改此规则，R01 脚本回放保持历史语义。
8. 不自动把非法 verdict 改为 unresolved 后当模型预测。executor status 和 model verdict 始终分栏。

## 5. C02 — 修复运行器边界，不做新的安全平台

### 5.1 validation 失败必须阻止模型调用

`validate_pilot_manifest` 失败时立即返回明确 blocked；测试必须证明模型加载/生成未发生。不要仅把 validation 对象放进 summary 后继续。

### 5.2 E0 必须是真正的前置门槛

使用包内 6 个自建微型案例：1 个 History note、2 个 SBS note、3 个 final；final 覆盖支持/反对/材料不足的普通函数要求，不涉及真实漏洞。

- 各案例最多初次+一次 schema_reprompt，共最多 12 次。
- 必须 6 个均 schema 合格且引用可绑定，才开放 E1。若某个 repair 后通过，照实记录 first-pass 不足。
- E0 自建 gold 仅评估端用于校准，不能出现在 actor 提示。E0 语义正确性另报：若 JSON 全有效但三个 final 与自建已知事实全部不符，不进入 E1，记录 `basic_reasoning_probe_failed`。一两个答错不作为隐蔽挑样本理由，照实保留。
- E0 不合格：停止新增真实样本调用，继续数据卡、测试、报告。**不再运行一整批后说 JSON 全军覆没。**

### 5.3 runtime 不读取 evaluator

在 prepare/管理端验证配对并生成**不含配对和标签**的 actor run manifest，只保留允许的 instance 根、冻结计划、哈希和 schedule。

runtime 不得调用 `count_complete_version_pairs` 或打开 `evaluator/pairs.jsonl`；不按 `instances[:2]` 猜测一对。管理端明确选定已登记 pair-01 的两个中性实例，输出仅含这两个实例的冻结列表；pair 映射只留 evaluator/管理报告。

runtime 可接收禁止路径用于拒绝读取，但不能读其内容。集成测试在准备完成后令 evaluator 读取抛错，runtime 仍必须能运行；这个测试不能只检查 IsolatedStore 自己的 flag。

本轮不搭建新容器/签名沙箱。只修数据依赖与白名单文件读取，执行器仍没有 shell/网络/自动审计工具。

### 5.4 完整 chat token 与实际可见正文

目前预算在最终指令、chat template 添加前计算。修复为：

1. 先固定 system/user 指令与输出契约，并用锁定 tokenizer 的实际 chat template 计 token；
2. 优先 `apply_chat_template(..., tokenize=True, add_generation_prompt=True)`；若先转文本再 tokenize，显式 `add_special_tokens=False`；
3. 保留模型输入张量的实际长度，整个实际输入≤3072 tokens；输出仍≤512；
4. 两组给 notes 同样 512-token 额度，给公共代码同样剩余额度；不足时共同 context_insufficient，不单侧截断；
5. 对真实发送的两组消息保存公共正文的 visible-byte hash、裁剪/遗漏说明、完整 prompt hash、token-id hash（或明确不可重建限制）；不能只比较裁剪前的逻辑对象 hash；
6. 真实请求中相同 instance、stage、证据日程的两组再做交叉核对，不能以“每组各自生成一对候选 prompt，自我比较通过”代替跨真实请求检查。

不要猜当前模型出现了重复特殊 token；本轮测实际序列并记录。锁定依赖版本，不为了跟 latest 文档升级所有库。

### 5.5 初始代码与证据数量

真实 `form` 请求必须看到同一份非空初始源码，不能仅有“Pinned source unit...”和泛化占位。

本轮固定首个源码单元为 initial evidence，在两组第一步都记录为 observed。后续按冻结日程读其他静态证据；没有其他证据就显式 no_more_material，不把同一证据重复登记为新增。

若仍只有一份证据：允许完成输出/记忆接口先导，但标签为 `single_evidence_interface_pilot`、`incremental_evidence_steps=0`，不能据此声称学习了证据选择或长期价值。

## 6. C03 — 数据与标注：补“可读内容”，不再堆数量

### 6.1 本轮只处理现有四对

固定对象：常规 pair-01、pair-12；逻辑草案 pair-13、pair-15。不重新筛选有利结果，不扩大 catalog，不抓新漏洞。

每对最多一页主卡，至少包含：实际组件/层次、两 revision 指针、每版材料列表与行号、完整方法还是片段、初始代码是否有行为、为何这个关系值得审查、遗漏什么。

### 6.2 先检查“短输入是否真的包含关键单元”

对现有 8 个实例逐一检查：

- 内容确实为对应 revision 的原始连续代码；不只是 imports、类声明、许可证或发布说明；
- 原文件 start/end 与实际片段逐行一致；
- `snippet_truncated=true` 或插入 truncated_middle 的，标非连续；不能把非连续拼接的正文伪标为单一原始行段；
- 现有 enclosing_java_unit 若提前遇到字段/内部括号就停止，要记录；不要仅因 body 哈希不同就声称方法完整；
- 本轮不写通用 Java parser。对于四对有限材料，可在管理端锁定经过检查的连续方法/配置范围，保存选择依据；不是在 runtime 按补丁搜索。

改变材料必须新 generation/manifest，不覆写 R02B。两版本源码相同片段本身不意味着记录伪造；“不同哈希”不是通用语义就绪标准。完整配对靠真实 revision 映射，语义区分是否有足够上下文另列。

### 6.3 两张逻辑要求卡必须实际填写

不再无条件硬编码 `obligation_generic=True`，也不能反过来直接设 False。根据下面的事实生成 requirement_status。

每张卡必填：

```text
pair_id / 实际组件
entities: 调用主体、被操作对象、相关上下文（来自源码，不是固定模板）
requirement_statement: 一项具体可讨论的关系
requirement_source: 文件/版本/段落或固定官方页面；找不到记 unknown
source_timing: 当时已存在 / 后来维护者澄清 / 模型推断
source_strength: 明确规范 / 代码配置或测试约定 / 相似代码线索 / 无依据
why_relevant: 两三句说明该要求与当前函数怎样有关
snapshot_left_evidence / snapshot_right_evidence: 非利用型解释与引用
alternative_explanation: 哪种合理解释可能让当前怀疑不成立
unknowns: 需要真人或更多规格回答的问题
context_complete: yes/no/unknown
requirement_status: missing / generic_only / concrete_unreviewed / disputed / human_confirmed
human_verified: false（除非用户已有可核对的实际记录）
```

来源优先对应冻结版本的文档、配置、注解、接口约定；历史维护者说明可以作 evaluator 参考但标明事后来源，不能悄悄加给 actor。CWE 类别和补丁改动本身不能替代规范。

只在必要时取这些已登记对象的官方静态文档；最多20个页面/20MiB，不打开利用步骤、不启动服务或样本构建测试。

每个逻辑对45分钟仍找不到要求：交付有内容的缺口卡，并明确下一步需要哪一项业务事实。不要继续用同一句模板反复宣称“待核验”。

### 6.4 真人核验单要让用户能直接判断

生成 `reports/rounds/R02C/HUMAN_CHECK.md`，最多提出两个主要问题，分别指向两张卡：

- 该具体关系是否确是该组件要求，而不是模型臆测？
- 给出的证据是否足以判断目标关系，还是遗漏上游/框架语义？

本地完整卡放 `local_data/r02c/evaluator/review_cards/`。Git 可放许可允许的最小非利用型摘录、释义、来源与不足；不能把整个第三方源码或答案包一股脑推送。

若远程仍无法读关键材料，则 `remote_content_review=partial/none`。不能把“有 hash”和“负责人已经核验语义”等同。没有真人确认，不填 accuracy/F1/GPC/reward。

### 6.5 同源分组只做有限且诚实的进展

对24条已登记元数据，优先登记上游 canonical repository identity、组织/仓库名字归一化、已知 fork/backport 关系。只从明确元数据映射，不能依据字符串各异宣称24个独立项目。

未知仍保留；`repository_group_count` 与 `independent_group_count` 分开。第一项核对可做，第二项不确定不阻塞本轮一对接口先导。所有现有样本仍 dev_pilot，未来不得突然划成干净 test。

## 7. C04 — 一次冻结、先 E0 再一对，不再重复跑全失败矩阵

### 7.1 预先冻结的配置

复用 R02B 的模型缓存、revision、CPU/float32、greedy、seed17、batch1。禁止更换模型、量化方式、隐式API提供者、训练权重或混入本地执行 agent 的对话上下文。

新增 `configs/r02c_pilot.lock.json`：记录基础模型、依赖、模板、三种输出schema、实际代码tree/config hash、材料generation、instance清单、固定证据日程、输入/输出上限、预算、重试规则。

本轮改变了协议，**R02B与R02C不能当作SBS性能前后对照**。旧响应仅离线诊断。新结果诚实命名 interface/state-flow pilot。

### 7.2 调用预算与旧账核对

预算构成：E0 6+至多6次重新生成；E1 一对两版本×两表示×四步=至多16个主请求，加至多16次重新生成；理论总计44，硬上限48不授权额外样本。

先生成 `legacy_request_reconciliation.json`：核对旧三个运行与稳定ledger。用已报告38作为旧消耗的下限，发现更多按更多算；若存在无法唯一合并事件，记录上下界并按保守上界限制新调用，不能把它们当零。

不能伪造38条历史 reservation 塞进新ledger；把可核对历史事件清单/基线与新预约记录分开保存。新运行在固定路径 `artifacts/r02c/request_ledger.jsonl` 增量写，项目总消耗通过冻结历史基线加后续真实记录计算：

```text
R02C 新预约数 ≤ 48
项目累计已预约/已报告保守消耗 ≤ 192
推理累计时间 ≤ 60分钟
```

每次生成前预约并落盘；崩溃保留 reserved_unknown，不退款偷跑。单一调用进程防止竞争，不搭建复杂队列。测试两次启动不重置、本轮结束后再次调用被拒绝/仅resume未完成项。

per-run attempts=`ledger_after-ledger_before`；ledger累计、项目累计各自列字段，不能继续把累计consumed当当前run请求数。原文相同不等于缓存命中；只有完全相同的模型/输入/条件/步骤/已完成请求身份才可复用，并标 cached，不计新调用。

### 7.3 主流程

1. C02回归、材料校验、模型身份和预算核对通过，固定实现提交A。
2. 实际 E0 六个案例；未过门槛就停止真实模型部分。
3. E0过后只跑 pair-01 的两个明确绑定实例，History与SBS各一条episode，四步日程固定。
4. 任何validation/实际输入公平性失败均停止E1，保留信息；不能当作一个普通模型错误然后继续。
5. 一个episode输出接口失败可结束该episode，其他条件按同一规则处理。若连续两个episode都因契约失败，停止剩余调用，记预先规定的circuit_breaker，不能挑替代样本。
6. 不用重新改提示后接着把剩余条件混成一组。E1开始后发现要改协议，则保存当前失败并停止本轮模型部分，下次由负责人决定。
7. 完整primary结果保存，初次成功、重新生成后成功、最终失败分开；不按是否支持论文叙事挑选。

### 7.4 本轮评价边界

可以统计：请求数与成本、围栏归一化比例、首次schema有效率、重新生成后有效率、引用形式合法率、状态实际更新数、未决/失败终止、公共正文一致性。

**不计算**真实数据 detection accuracy/F1/GPC、目标语义正确率、reward、Q accuracy。没有真人标签仍可报告产生了哪些真实可读回答，但不能以它们训练价值。

必须在 ANALYSIS 中展示至少一条（若有）状态变化链：初始假设→新材料/明确无新材料→支持与反证/未知项的变动→最终模型结论或执行器失败。不可仅给“JSON成功了”一个百分比。

## 11. 完成标准与下一轮决策材料
